FEATURE 01. 확장 가능한 Enemy AI Architecture

문제

Enemy의 종류가 늘어날수록 Patrol, Target 탐색, 추적, 조사, 전투 같은 공통 행동이 반복되는 한편, 각 Enemy마다 다른 세부 행동도 필요합니다. Enemy별 Behavior Tree 전체를 복제하면 공통 정책이 중복되고, 하나의 거대한 Tree에 모두 넣으면 타입별 분기가 빠르게 복잡해집니다.

Sight, Hearing, Damage 이벤트가 각자 상태를 변경할 때 생기는 전환 충돌과 Target 사망 뒤 남는 Blackboard 값도 함께 해결해야 했으며, 멀티플레이에서는 클라이언트마다 다른 판단이 나오지 않도록 서버 권한 구조가 필요했습니다.

목표

  1. 모든 Enemy가 공유하는 상위 AI 상태와 Root Behavior Tree를 정의합니다.
  2. AI Perception의 Sight, Hearing, Damage를 하나의 Controller에서 처리합니다.
  3. Enemy별 행동은 상태 단위 Subtree로 분리하고 DataAsset에서 교체합니다.
  4. Target 사망 또는 인식 해제 시 유효한 Target을 재탐색합니다.
  5. 상태 변경과 Target 결정은 서버에서만 수행합니다.

설계

상위 상태와 책임 분리

EEnemyAIState를 Passive, Investigating, Combat, Frozen, Dead로 정의했습니다. 이 값은 세부 행동 자체가 아니라 현재 의도와 Behavior Tree 실행 방향을 결정하는 상위 상태입니다.

state flow 
Passive
   ├── Hearing ─────────────→ Investigating
   └── Sight / Damage ──────→ Combat
                                  ├── Target 상실 → Passive
                                  └── Enemy 사망 → Dead

AI Perception은 “무엇을 인식했는가”만 판단하고, Blackboard에 State, TargetActor, PointOfInterest, HomeLocation을 기록합니다. Behavior Tree는 이 공유 상태를 기준으로 “무엇을 할지”를 결정합니다.

Root Behavior Tree + Dynamic Subtree

공통 Root Behavior Tree는 상태 분기와 Target 관리 같은 공통 정책을 담당합니다. Enemy 타입별 세부 행동은 UEnemyBehaviorSet DataAsset에 상태, Injection Tag, Subtree를 매핑하고 SetDynamicSubtree()로 주입합니다.

architecture 
ABaseEnemy
   ├── Shared Root Behavior Tree
   └── EnemyBehaviorSet DataAsset
          ├── Passive → Passive Subtree
          ├── Investigating → Investigation Subtree
          └── Combat → Enemy-specific Combat Subtree

구현

Possess 시 초기화

ABaseAIController::OnPossess()에서 Blackboard를 초기화하고 Home Location, Patrol Radius, 초기 상태를 설정한 뒤 Root Tree를 실행하고 Behavior Set을 적용합니다. Target과 Point of Interest는 초기화하여 이전 실행 상태가 남지 않도록 했습니다.

Perception 기반 상태 전환

  • Sight: 유효 Actor를 발견하면 SetCombatTarget()에서 캐시, Blackboard, 사망 Delegate, Combat 전환을 한 번에 처리합니다.
  • Hearing: 소리 위치를 Point of Interest로 저장하고 Investigating으로 전환하되 Combat, Frozen, Dead 상태는 덮어쓰지 않습니다.
  • Damage: 시야 밖에서 공격받더라도 공격자를 즉시 Combat Target으로 지정합니다.

Target 사망과 재탐색

현재 Target의 Health Component 사망 Delegate를 구독합니다. 사망 시 마지막 위치를 남기고 Target과 Focus를 제거한 뒤, 현재 Sight로 감지 중인 공격 가능 Actor만 필터링해 가장 가까운 대상을 재선택합니다.

target lifecycle 
Current Target Death
        ↓
Target / Focus 정리
        ↓
Reacquire Delay
        ↓
Currently Perceived Actors 조회
        ↓
공격 가능 여부 필터링
        ↓
가장 가까운 유효 Target 선택

서버 권위

SetEnemyState(), SetCombatTarget(), StartInvestigation()과 Perception 처리에 Authority 검사를 두었습니다. 서버는 AI 판단과 Blackboard 변경을 담당하고, 클라이언트는 복제된 Enemy 결과를 표현합니다.

결과

공통 정책 재사용Enemy가 늘어나도 Root Tree를 반복 제작하지 않습니다.
일관된 상태 관리Target과 상위 상태를 Blackboard의 단일 흐름으로 관리합니다.
데이터 기반 확장Enemy Archetype별 Subtree 조합을 DataAsset에서 변경합니다.
멀티플레이 안정성서버가 Target과 상태 전환의 최종 권한을 가집니다.

핵심 구현 포인트 — AI Perception이 직접 행동하지 않고 상위 상태를 갱신하며, 공통 Root Tree에 Enemy별 상태 Subtree를 동적으로 주입했습니다.

개선점

  • 상태가 늘어날 때를 대비해 허용·금지 전환을 별도의 Transition Rule로 명시합니다.
  • 거리뿐 아니라 체력, 최근 Damage, 역할과 Aggro를 포함한 Target Score 정책으로 확장합니다.
  • 현재 상태, Target, 마지막 Stimulus, 실행 중 Subtree를 Gameplay Debugger에 표시합니다.

FEATURE 02. EQS + GAS 기반 Enemy Combat

문제

원거리 Enemy가 Target을 향해 이동한 뒤 사거리 안에서 바로 공격하면 지나치게 가깝거나 먼 위치, 장애물 뒤처럼 Line of Sight가 없는 위치에서도 공격을 시도할 수 있습니다. 여러 Enemy가 같은 위치를 고르면 전투 패턴도 반복적으로 보입니다.

Behavior Tree에서 Animation과 Damage까지 직접 처리하거나 Montage 길이에 맞춰 고정 Wait를 두면, 공격 속도와 Animation이 바뀔 때 실제 공격 생명주기와 AI Task 완료 시점이 어긋납니다.

목표

responsibility 
EQS             → “어디에서 공격할 것인가?”
Behavior Tree   → “언제 이동하고 공격할 것인가?”
GAS             → “실제 공격을 어떻게 실행할 것인가?”

Target 주변의 유효한 사격 위치를 검색하고, 이동 후 최종 공격 가능 여부를 재검사하며, 실제 Animation, Projectile과 Damage는 서버에서 실행되는 Gameplay Ability에 맡기는 것을 목표로 했습니다.

설계

EQS 전투 위치 선정

Target 주변에 Donut 형태의 후보 지점을 생성합니다. 각 후보는 Target과의 거리, 현재 Enemy와의 Reposition 거리, Path 존재 여부, Target까지의 Line of Sight를 통과해야 합니다. 최고점 하나를 고정하지 않고 RandomBest25Pct로 상위 후보군에서 선택해 반복을 줄였습니다.

eqs query 
Target 중심 Donut 후보 생성
        ↓
공격 거리 · Reposition 거리 평가
        ↓
Pathfinding 가능 여부 필터
        ↓
Target Line of Sight 필터
        ↓
Score 상위 25% 중 위치 선택

Behavior Tree 전투 흐름

Combat Branch 진입 시 공격 가능 여부로 전체 흐름을 막지 않습니다. 먼저 EQS로 Reposition할 기회를 주고, 이동을 마친 직후 Range와 Line of Sight를 다시 검사한 뒤 공격 Task를 실행합니다.

combat flow 
Combat Target 확인
      ↓
EQS Combat Position 검색
      ↓
PointOfInterest로 MoveTo
      ↓
최종 Range / LOS 재검증
      ↓
BTT_RangedAttack
      ↓
Gameplay Ability 활성화

GAS 공격 생명주기

원거리 공격 Ability는 ServerOnly로 실행됩니다. 활성화 시 Target과 LOS를 다시 확인하고 State.Attacking Gameplay Tag를 추가합니다. Montage의 발사 Frame에서 Gameplay Event를 받아 Projectile을 만들고, Montage 종료와 함께 Ability 및 공격 상태를 정리합니다.

구현

하나의 Target Source 공유

EQS Context는 별도의 Target 복사본을 갖지 않고 AIController의 CachedTargetActor를 사용합니다. Blackboard, AIController와 EQS가 같은 Runtime Target을 바라보므로 서로 다른 대상을 평가하는 문제를 막았습니다.

공격 직전 Line of Sight 재검증

Attack Origin에서 Target까지 Visibility Trace를 수행합니다. Enemy 자신과 Host Ship은 제외하고, 장애물이 맞으면 공격을 중단하며 Target이 맞거나 Blocking Hit이 없을 때만 공격을 허용합니다. EQS 이후 Target 이동이나 환경 변화로 판단이 낡는 상황을 방어합니다.

BT Task와 Ability 종료 동기화

UBTT_RangedAttack은 Ability 활성화 뒤 고정 시간을 기다리지 않습니다. OnAbilityEnded Delegate를 구독하고 실제 Ability가 끝날 때 Task를 성공 또는 실패로 완료합니다. Ability가 Cancel되면 Task도 실패 처리됩니다.

async sync 
BT Task = InProgress
        ↓
Gameplay Ability Activate
        ↓
Montage Fire Event
        ↓
Projectile Deferred Spawn · GameplayEffect 설정
        ↓
Ability Ended Delegate
        ↓
BT Task = Succeeded / Failed

Montage Frame과 Projectile 동기화

UAbilityTask_WaitGameplayEvent가 발사 Frame 이벤트를 기다립니다. Event 수신 시 SpawnActorDeferred로 Projectile을 만들고 Source ASC, Damage Gameplay Effect, Owner와 Instigator를 설정한 뒤 발사합니다. Event 누락 시 Montage 완료 지점에서 한 번 발사하는 Fallback도 두었습니다.

공격 상태와 서버 권한

공격 중 상태는 Behavior Tree 전용 Boolean이 아니라 GAS의 State.Attacking Tag로 공유합니다. Ability Activation, Projectile Spawn과 GameplayEffect Damage는 서버에서 처리하고 클라이언트는 결과와 Animation을 표현합니다.

결과

공간 판단 분리EQS가 거리, Path, LOS를 함께 평가해 공격 위치를 선택합니다.
오래된 판단 방지이동 후 Range와 LOS를 다시 확인합니다.
비동기 수명 동기화Delegate와 Event가 BT, Ability, Montage를 연결합니다.
서버 기준 전투Projectile과 Damage의 판정 기준을 서버에 둡니다.

핵심 구현 포인트 — EQS는 위치, Behavior Tree는 순서, GAS는 실행을 맡고 Delegate와 Gameplay Event로 서로 다른 비동기 시스템을 동기화했습니다.

개선점

  • Cover, 위험 지역, 지형 높이, 다른 Enemy와의 거리, 최근 사용 위치 감점을 EQS 평가에 추가합니다.
  • Target 이동, LOS 상실, 기존 위치 무효화 때만 EQS를 재실행하고 AI LOD로 빈도를 조절합니다.
  • 근거리와 원거리 공격을 공통 BTTask_ActivateEnemyAbility 계층으로 통합합니다.

FEATURE 04. Data-Driven Wave & Route System

문제

Wave를 SpawnActor와 Timer만으로 구성하면 Enemy 종류, 수, 시작 시간, 생성 간격, Burst, Route와 난이도 배율이 코드에 쌓입니다. 모든 Enemy가 같은 Waypoint 중심을 따라가면 겹치고, Spline Point 사이가 길면 곡선 대신 직선으로 이동하려는 문제도 생깁니다.

Enemy마다 Tick에서 Waypoint 거리를 검사하는 방식은 개체 수가 증가할수록 반복 연산이 늘어납니다. 콘텐츠 설정과 Runtime 진행 상태, 이동 완료 감지를 각각 분리할 필요가 있었습니다.

목표

  1. Wave 정적 설정을 DataAsset으로 분리하고 여러 Spawn Group을 독립 실행합니다.
  2. Count, Interval, Burst, Delay, Route와 Scaling을 데이터에서 설정합니다.
  3. Spline을 Route로 사용하고 긴 구간에는 Support Waypoint를 자동 생성합니다.
  4. Waypoint와 Offset 위치를 NavMesh에 Projection합니다.
  5. Enemy별 deterministic Offset으로 같은 Route의 이동 위치를 분산합니다.
  6. Tick 대신 PathFollowing Event로 다음 Waypoint를 진행합니다.
  7. 사망, 목표 도달, 실패를 Wave 생명주기에 연결하고 서버가 실행을 관리합니다.

설계

정적 데이터와 Runtime State 분리

UWaveDataAsset은 Enemy Class, Count, Route ID, Start Delay, Spawn Interval, Burst Count, Spawn Radius, Health와 Speed Multiplier, Enemy Level 같은 콘텐츠 설정만 보관합니다. 현재 생성 수와 Timer는 FSpawnGroupRuntime에 따로 둡니다.

data model 
WaveDataAsset       → “어떻게 생성할 것인가?”
  └── WaveDefinition
        ├── Spawn Group 0
        ├── Spawn Group 1
        └── Spawn Group 2

SpawnGroupRuntime   → “현재 얼마나 생성했는가?”

WaveSpawnManager 생명주기

AWaveSpawnManager는 서버에서 Pre-Wave Delay, Group별 Start Delay와 Timer, Enemy Spawn, Active Enemy Count, 완료 조건을 관리합니다. 모든 Group의 생성 완료와 AliveEnemyCount == 0가 함께 만족될 때 Wave가 끝납니다.

Spline Route와 Support Waypoint

레벨 디자이너가 배치한 ASpawnRoute Spline을 Runtime Waypoint로 변환합니다. 두 Designer Point 사이가 설정한 최대 길이보다 길면 Support Waypoint를 자동으로 삽입하고, 각 위치를 NavMesh에 Projection해 실제 이동 가능한 경로로 보정합니다.

Deterministic Route Offset

Enemy가 Waypoint 중심에 겹치지 않도록 Route Width 안에서 Lateral과 Forward Offset을 적용합니다. EnemySeed + WaypointIndex로 FRandomStream을 만들기 때문에 같은 조건은 같은 결과를 재현합니다.

구현

Spawn Group과 Burst 실행

Wave 시작 시 Group별 Runtime 상태를 만들고 각자의 Start Delay 이후 독립 실행합니다. 예를 들어 Count 10, Burst 3, Interval 1초인 Group은 3, 3, 3, 1마리 순서로 생성됩니다. Interval이 0 이하라면 남은 수를 즉시 처리하는 별도 흐름을 사용합니다.

Enemy Spawn과 Route 연결

Spawn Group의 Route ID로 Route Map에서 ASpawnRoute를 찾고 Spawn Transform을 얻습니다. Enemy 생성 뒤 AIController, Route Seed, Death와 Route Delegate, Health·Speed·Level Scaling을 초기화하고 WaypointMoveComponent.StartRoute()를 호출합니다.

Seed 생성과 Offset 재현

Seed Base, Wave Index, Group Index, Group 내 Spawn 순번과 Serial Counter를 Hash해 Enemy Route Seed를 만듭니다. 각 Waypoint Index와 결합해 Offset을 계산하므로 같은 Route에서도 Enemy별 경로가 분산되고 디버깅 시 재현할 수 있습니다.

NavMesh Projection과 실패 복구

Raw Spline Point와 Offset Target을 Navigation System으로 Projection합니다. Offset 위치가 실패하면 중심점 방향으로 Offset을 줄여 재시도하고, 최종적으로 Waypoint Center를 Fallback으로 사용합니다. MoveTo 실패 시에도 중심점으로 제한 횟수만큼 재시도한 후 실패 이벤트를 보냅니다.

Event-Driven Waypoint Movement

UEnemyWaypointMoveComponent는 Tick을 사용하지 않습니다. Move Request ID를 저장한 뒤 UPathFollowingComponent::OnRequestFinished를 구독하고, 자신의 요청이 완료되었을 때 다음 Waypoint로 이동합니다.

route flow 
MoveTo(Current Waypoint)
        ↓
PathFollowing Request ID 저장
        ↓
OnRequestFinished
        ↓
Next Waypoint 또는 Goal Reached
        ↓
WaveSpawnManager에 제거 사유 전달

Enemy 제거와 Wave 완료

Manager는 Enemy를 Active Set으로 추적하며 Death, Goal Reached, Despawn을 하나의 제거 흐름으로 처리합니다. 제거 이벤트가 중복되어도 Removed Set으로 방어해 Alive Count가 두 번 감소하지 않습니다. Wave 진행 상태 변경과 Enemy Spawn은 모두 서버에서 실행합니다.

결과

데이터 중심 콘텐츠Wave 구성과 Spawn Pattern을 코드 수정 없이 변경합니다.
디자이너 친화 RouteSpline과 자동 Support Point로 곡선 경로를 구성합니다.
분산과 재현성Deterministic Offset으로 겹침을 줄이고 결과를 재현합니다.
이벤트 중심 이동Tick 없이 PathFollowing 완료 이벤트로 이동을 진행합니다.

핵심 구현 포인트 — Wave 데이터를 DataAsset으로 분리하고 Spline을 Runtime Waypoint로 변환한 뒤, deterministic Offset과 PathFollowing Event로 다수 Enemy의 생성과 이동을 관리했습니다.

개선점

  • GAS, Blackboard, Delegate와 Route 상태를 안전하게 Reset하는 Enemy Object Pool을 도입합니다.
  • RVO, Detour Crowd, EQS Local Reposition 또는 Lane 데이터로 Route 혼잡을 줄입니다.
  • GameState에 Wave 번호, 남은 시간, Alive Count 같은 UI 최소 데이터만 복제합니다.
  • 거리와 중요도에 따라 Perception, BT Service, EQS, Animation 업데이트를 조절하는 AI LOD를 적용합니다.
